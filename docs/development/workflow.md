# 开发与提交工作流

## 工作单元

默认以一个“小而完整的分支目标”作为工作单元。目标应当可以用一句话描述，并拥有可验证的完成条件，例如：

- 建立 Python 工程和质量检查；
- 加入 Player 与 Alliance 的首个数据库迁移；
- 完成 `StartMining` 用例及其测试；
- 接入一个 Discord 命令；
- 修复一个明确缺陷并增加回归测试。

如果一个目标开始同时涉及多个独立结果，应先拆成更小目标，而不是把大量无关改动积累到一次提交中。

## 何时提交

完成一个小目标后应主动创建本地提交，不必等待整个里程碑结束。以下情况也是合适的提交点：

- 一个架构或产品决策已经完整记录；
- 一次重构保持现有行为且相关检查通过；
- 数据迁移与对应模型已经形成可独立验证的整体；
- 工作即将进入明显不同的模块或风险阶段；
- 为后续实验建立了稳定、可回退的基线。

不要把无法运行的半个功能作为普通完成提交。如果确实需要保存探索性检查点，应在提交信息中明确标注其性质，并确保不会被误认为已交付能力。

## 提交前检查

检查强度与改动风险相称，但至少应当：

1. 查看 diff，确认没有混入无关文件、密钥或本地生成物。
2. 运行受影响范围的格式检查、静态检查和测试。
3. 确认文档、迁移和接口契约与实现同步。
4. 确认提交可以独立解释，并且回退它不会破坏其他不相关目标。

若因环境或外部服务无法运行某项检查，可以提交，但必须在交付说明中明确未验证内容和原因。

## 提交内容与信息

- 一个提交表达一个主要意图，不混合格式化、重构和新功能等独立工作。
- 提交信息使用简洁的祈使式摘要，优先采用 `docs:`、`build:`、`test:`、`feat:`、`fix:`、`refactor:` 等前缀。
- 数据库迁移必须与使其成立的模型或用例一起提交。
- 可复现构建所需的锁文件应提交，缓存、虚拟环境和密钥不得提交。
- 不修改、压缩或重写用户已有提交，除非用户明确要求。

## 分支与远端

- 当前 Python 重写工作发生在 `python-rewrite` orphan 分支及其 worktree 中。
- 本地提交属于日常开发授权范围；完成自然工作单元时可以主动提交。
- 提交不等于发布。除非用户明确要求，不主动 push、创建远端分支、合并或变基。
- 每个里程碑可以包含多个小提交；里程碑是否完成仍以其文档中的验收标准为准。
