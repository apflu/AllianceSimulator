# 旧项目检查结论

## 来源

旧实现位于 `D:\\workspace\\AllianceSimulator`，主要开发时间为 2024 年 11 月至 12 月，使用 Java 17、少量 Kotlin、Gradle、JLine、协程和未落地的 Exposed 数据库依赖。

## 可继承的产品意图

- Alliance 是玩家控制主体，拥有模拟成员和状态旗标；
- 角色通过技能计划长期成长；
- 舰船在星系与地点中执行采矿和战斗；
- 主动模块以周期方式产生效果；
- 条件事件进入联盟待处理队列，玩家选择选项；
- 事件可以组成事件链，并包含固定或随机延迟；
- 服务器持续运行，并计划加入保存和 tick 机制。

## 不应迁移的实现方式

- Java/Kotlin 单例管理全部游戏状态；
- 每个模块或技能更新器拥有常驻内存协程；
- 游戏输出直接绑定 JLine 控制台；
- 以继承树表达所有物品、装备和事件；
- 未完成 Builder 返回 `null`；
- 用全局可变集合代替数据库和事务；
- 查询期间隐式生成或改变世界状态；
- 只验证“代码能运行”的里程碑程序，而没有行为测试。

## 已发现的典型问题

- 多个关键路径仍为 TODO，包括舰船构建、地点注册、事件队列和服务器循环；
- 采矿路径会对矿石体积重复扣减；
- 延迟事件的 `after()` 设计可能递归调用自身；
- Listener 注册逻辑条件倒置，通知路径可能访问空集合；
- 唯一正式测试恒定成功，不能证明玩法正确；
- 数据库依赖存在，但没有持久化模型和迁移。

## 迁移原则

旧仓库作为需求考古资料保留。新项目可以重新表达技能公式、舰船内容和事件构想，但每一项都必须先成为清晰的行为规格和测试，不能逐文件翻译旧代码。
